# CUI → ZZUI 迁移审计（2026-11-10）

> 审计口径：**全部数字来自脚本实测**，不是估计。
> 采样脚本：扫描 `C:\Code\C\CUI\src\*.c` 的公开函数定义与 `include/cui/cui.h` 的声明，
> 扫描 `src/*.zig` 的 `pub fn`；映射表按「语义对位」人工建立后由脚本计算覆盖率。
> 复现方式见文末「复现命令」。

## 1. 结论先说（是否「迁移完成」）

**没有全量迁移完成。已完成的是「基础控件七族」，占 CUI 控件类 API 的约 22%。**

| 维度 | CUI | ZZUI | 完成度 |
|---|---|---|---|
| 公开 API（去重，按文件定义统计） | **467** | 77 个 `pub fn`（其中 58 个是控件函数） | 按 API 名对位 **92 个 = 19.7%** |
| 控件类 API（剔除 core/draw/text/theme/layout/strings/regex/image 共 96 个基础设施） | **371** | 99 个对位 | **26.7%** |
| 源码行数（src） | **51,486 行 C**（61 个 .c） | **5,760 行 Zig**（12 个 .zig） | 11% |
| 后端 | 5（win32 / cocoa / x11 / sdl2 / glfw） | **2**（win32 / null） | 40% |
| 渲染器 | 2（软件 + OpenGL） | **1**（软件 BGRA） | 50% |
| 测试 | 22 个文件 / ~94 个用例 | 1 个文件 / **45 个用例**（含 3 个全控件冒烟） | 48% |
| 示例 | 16 个 | **2**（hello / gallery 四页） | 12% |
| hello 产物 | **296.0 KB**（C，`zig cc -Os`） | **169.5 KB**（x64）/ 170.5 KB（x86）；最小 ZZUI 程序 146.5 KB | 见 §1.1 口径 |


### 1.1 体积口径（重要，避免误读）

**「体积」指实际生成的 `.exe` 字节数**，不是代码行数、不是内存占用。具体构建口径：

- Zig `-Osmall`（ReleaseSmall）+ `-fstrip`（去符号）
- `-target x86_64-windows-gnu` / `x86-windows-gnu`（`.abi = .gnu`，**不链 libc / UCRT**）
- `--subsystem windows`（GUI 子系统，无控制台）
- 报的是 PE 文件长度（`Get-Item *.exe | Select Length`）

四个实测基线（同口径，2026-11-10）：

| 程序 | 体积 | 说明 |
|---|---|---|
| **空 Windows GUI 程序**（只有 `wWinMain { return 0; }`，不含 ZZUI） | **4,608 B（4.5 KB）** | Zig 空程序基线 |
| **最小 ZZUI 程序**（`initHeadless` + 一帧 + 1 个文本节点） | **150,016 B（146.5 KB）** | 框架静态成本（含 Win32 后端 + 软件光栅 + 核心 + 文本测量） |
| **hello**（真实窗口 + 基础控件） | **173,568 B（169.5 KB）** | 上者 + 23.5 KB 控件代码 |
| **gallery**（59 个控件 + 表格 + 图表，分 5 页） | **216,576 B（211.5 KB）** | 上者 + 全部控件/表格/图表 ≈ 66.6 KB |

**由此得到的结论**：
1. **框架本身占大头**：146.5 KB / 169.5 KB ≈ **86%** 的 hello 体积是框架（后端 + 光栅 + 核心），控件只占 23.5 KB。
2. 所以要压体积，优先压**框架**（后端、光栅、文本测量），而不是砍控件；
   但如果只是「加一个控件」，增量通常是 1~3 KB 量级 —— 这也解释了为什么 A 档 52 个 API 预估只增 < 15 KB。
3. **与代码体积脱节的两处**（实测）：
   - `MAX_NODES` 等容量常量变大 → 产物 +79 KB（不是代码变多，是 `Context` 变大后编译器生成的初始化/搬运代码变多）；
   - `std.fmt` 浮点格式化 → 几十 KB（拉进了整套浮点格式化实现）。
4. **与 CUI 的可比性**：CUI hello 296.0 KB 与 ZZUI hello 169.5 KB 都是「各自的最小演示」，
   功能集合不同（CUI hello 带的组件更多），所以只能说明「ZZUI 的最小演示更小」，
   **不能**推出「同等功能下 ZZUI 更小」——这需要同一界面的双实现对比（目前未做，属审计缺口）。

**复现命令**（可独立运行，不依赖 build.zig）：

```powershell
# 空程序基线
zig build-exe -Osmall -fstrip -target x86_64-windows-gnu --subsystem windows `
  --name min_empty "-femit-bin=artifacts/min_empty.exe" .git/min.zig
# 最小 ZZUI 程序
zig build-exe -Osmall -fstrip -target x86_64-windows-gnu --subsystem windows --dep zzui `
  "-Mroot=.git/min_zzui.zig" "-Mzzui=src/zzui.zig" `
  --name min_zzui "-femit-bin=artifacts/min_zzui.exe"
```

## 4. 已迁移但「简化」的差异（不是没做，是做窄了）

| 能力 | CUI | ZZUI 现状 |
|---|---|---|
| 动画 | tween + spring（hover/press/focus 全插值） | **无**；只 `spinner` 用帧时间做相位 |
| 阴影 | elevation 阴影、光泽（sheen） | **无**，浮层靠 1px 边框区分 |
| 焦点环 | 动画焦点环 | 静态 1px 强调色环 |
| 文本 | 字体加载/回退链、bidi、emoji、富文本 | 系统字体单字体；`wrapText` 支持空格/连字符/CJK 断点 |
| 输入 | 选区、撤销栈、词级移动、IME 候选窗 | 单行/多行编辑 + 光标，**无选区/撤销/词移动** |
| 滚动 | 滚动条拖拽、惯性、水平滚动 | 滚轮 + 跟随光标，**滚动条不可拖** |
| 表格 | 列宽拖拽、多选、固定列、内联编辑 | 只读流式表格 + 行选中 + 排序回调 |
| 浮层 | 弹出层栈、多点定位、自动翻转全向 | 单层栈、下/上方翻转、窗口内夹取 |
| 平台 | 5 后端 + IME/剪贴板/文件拖放/DPI 每屏 | Win32 单后端；无 IME 控制、无剪贴板、无拖放 |

## 6. 代码质量审计（ZZUI 自身，实测）

| 检查项 | 结果 |
|---|---|
| `TODO` / `FIXME` / `unimplemented` | **0 处**（`src` + `examples`） |
| 空 `catch {}` / `catch null` / 吞错误 | **0 处** |
| `std.fmt` 浮点格式残留 | **0 处**（全部走 `num.fixed`，实测该替换把 gallery 从 296,448 B 降到 291,328 B） |
| 容量溢出护栏 | `Context.overflowed` 在 4 处（nodes / commands / overlays / hits）置位；**Debug 构建额外打印来源**（`markOverflow`，发布构建不生成字符串，体积实测无变化） |
| 单测 | **42 个用例**；其中 3 个是**全控件冒烟**（widgets+extras / controls+textedit+overlay / table+charts 各建一遍并断言不溢出） |
| 控件函数被单测直接调用 | 33/63（52%）；加上 3 个冒烟用例后，**63/63 个控件函数都被实际构建过** |
| 回归 | `REGRESSION PASSED (skip=0)`：构建 + 单测 + 体积门槛 + 三份 BMP 像素断言 + gallery 四页断言 + 接续自检 + 文档齐全 |

### 7.1 本次审计发现并已修的真问题

1. **线段预算先于节点预算被打满**：`table + charts` 同页时 `MAX_OVERLAYS`（192）被打满（实测 `lines=192/192`），
   版面看起来「图表缺一块」。根因是面积填充用粗线段（53 条/图）+ 圆弧 20 段/圈。
   **修法**：面积填充改**宽矩形条**（每 20px 一条，占节点预算 32 个/图，节点余量 152/256 更宽松）；
   圆弧收紧到 16 段/圈、半圆 12 段。修后实测 `nodes=152/256 cmds=266/512 lines=83/192 hits=16/128`。
2. **`MAX_OVERLAYS` 不能随便提**：从 192 提到 384 让 hello x64 **+13,824 B（+13.5 KB）**（实测），
   所以正确做法是**降绘制成本**，不是扩容。
3. **容量溢出必须可见**：给 `markOverflow` 加 Debug 打印后，同一测试 5 秒内就指出是 `overlays` 而不是 `nodes` ——
   没有这条打印只能靠猜。这条经验已写入项目记忆。

### 7.2 仍未覆盖的审计盲区（明确记录，不假装覆盖）

| 盲区 | 原因 | 影响 |
|---|---|---|
| 真实窗口的鼠标拖拽/滚轮/键盘长跑 | 回归只有 headless + 一次性隐藏窗口渲染 | 长时运行的资源占用（CPU/内存）未测 |
| IME 输入 | Win32 后端未处理 `WM_IME_*` | 中文候选窗不可控（`ZZCOM` 有 `ImmAssociateContext(null)` 的先例可借鉴） |
| 多显示器 / 每屏 DPI | 只取主屏 DPI | 拖到不同 DPI 屏幕会发虚 |
| 剪贴板 | 未接 `OpenClipboard` | `copyButton` 只返回点击，复制由调用方做 |
| 文件拖放 | 未接 `WM_DROPFILES` | CUI 有 `cui_dropped_file`，ZZUI 无 |

## 7. 建议的下一步（按「体积优先 + 高频优先」排序）

1. **A 档一批做完**（disclosure + chrome + actions + dials + code + hex，约 52 个 API）——
   全是线段/矩形/文本，预估体积增量 < 15 KB。
2. **viz 的四个低成本件**（heatmap / bar_list / split_bar / radial_gauge）。
3. **grid 增强**（列宽拖拽 + 内联编辑 + filter_bar）—— 让 `table.zig` 追上 `cui_data_grid`。
4. **平台**：X11/Cocoa 后端（需先在 WSL 里能实测 X11，否则按「实测优先」不开工）。
5. C 档（编辑器/终端/diff/markdown/emoji/位图）**明确不排期**，除非有具体产品需求。

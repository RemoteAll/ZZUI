### 1.1 体积口径（重要，避免误读）

**「体积」指实际生成的 `.exe` 字节数**，不是代码行数、不是内存占用。具体构建口径：

- Zig `-Osmall`（ReleaseSmall）+ `-fstrip`（去符号）
- `-target x86_64-windows-gnu` / `x86-windows-gnu`（`.abi = .gnu`，**不链 libc / UCRT**）
- `--subsystem windows`（GUI 子系统，无控制台）
- 报的是 PE 文件长度（`Get-Item *.exe | Select Length`）

四个实测基线（同口径，2026-11-10）：

| 程序 | 体积 | 说明 |
|---|---|---|
| **空 Windows GUI 程序**（只有 `wWinMain { return 0; }`，不含 ZZUI） | **4,608 B（4.5 KB）** | Zig 空程序基线 |
| **最小 ZZUI 程序**（`initHeadless` + 一帧 + 1 个文本节点） | **153,088 B（149.5 KB）** | 框架静态成本（含 Win32 后端 + 软件光栅 + 核心 + 文本测量） |
| **hello**（真实窗口 + 基础控件） | **181,760 B（177.5 KB）** | 上者 + 24.5 KB 控件代码 |
| **gallery**（全量控件装载，分 13 页） | **330,752 B（323 KB）** | 上者 + 全部控件 ≈ 168 KB（门槛 328 KB，见 §1.2） |
| **pickers**（选择器 + 拖放/头像 + 图片查看裁剪 + 媒体动效 + BMP 解码，18 控件单产物） | **249,344 B（243.5 KB）** | 这些族单独扛一个演示，不塞 gallery（门槛 248 KB，见 §1.2） |

**由此得到的结论**：
1. **框架本身占大头**：146.5 KB / 169.5 KB ≈ **86%** 的 hello 体积是框架（后端 + 光栅 + 核心），控件只占 23.5 KB。
2. 所以要压体积，优先压**框架**（后端、光栅、文本测量），而不是砍控件；
   实测增量：A 档 26 个 API / 24 个控件 **+39.9 KB**（1.7 KB/控件）；B 档的可视化/曲线 17 个 API **+25.5 KB**（1.5 KB/控件）；B 档的网格/树表/面包屑/筛选条 16 个 API **+17.4 KB**（1.1 KB/控件）；B 档的停靠 9 个 API **+15.9 KB**（1.8 KB/控件，含布局串解析器与递归布局）；B 档的选择器 13 个 API **+24.1 KB**（1.9 KB/控件，独立产物 173,568 → 197,632 B）；B 档的媒体动效 10 个 API **+16.9 KB**（含渲染分层基础设施 1.5 KB，pickers 224,256 → 241,152 B）；**图片解码按格式付费**（实测）：BMP **+1,024 B**、PNG（inflate）**+13,312 B**。
3. **与代码体积脱节的两处**（实测）：
   - `MAX_NODES` 等容量常量变大 → 产物 +79 KB（不是代码变多，是 `Context` 变大后编译器生成的初始化/搬运代码变多）；
   - `std.fmt` 浮点格式化 → 几十 KB（拉进了整套浮点格式化实现）。
4. **与 CUI 的可比性**：CUI hello 296.0 KB 与 ZZUI hello 169.5 KB 都是「各自的最小演示」，
   功能集合不同（CUI hello 带的组件更多），所以只能说明「ZZUI 的最小演示更小」，
   **不能**推出「同等功能下 ZZUI 更小」——这需要同一界面的双实现对比（目前未做，属审计缺口）。

**复现命令**（可独立运行，不依赖 build.zig）：

```powershell
# 空程序基线
zig build-exe -Osmall -fstrip -target x86_64-windows-gnu --subsystem windows `
  --name min_empty "-femit-bin=artifacts/min_empty.exe" .git/min.zig
# 最小 ZZUI 程序
zig build-exe -Osmall -fstrip -target x86_64-windows-gnu --subsystem windows --dep zzui `
  "-Mroot=.git/min_zzui.zig" "-Mzzui=src/zzui.zig" `
  --name min_zzui "-femit-bin=artifacts/min_zzui.exe"
```

### 1.2 两个产物、两条门槛（不要把口径混在一起）

回归脚本原本用**同一个 303,104 B**卡三个产物，这在 gallery 加载全部控件后就不再成立：

| 产物 | 含义 | 门槛 | 现状 |
|---|---|---|---|
| `zzui-hello-*.exe` | **最小应用**（窗口 + 基础控件） | **303,104 B**（CUI hello 296 KB 基线，只能收紧） | 192,000 B（x64）/ 188,416 B（x86） |
| `zzui-gallery-x64.exe` | **全量装载演示**（全部控件，13 页） | **344,064 B（336 KB）** | **341,504 B** |
| `zzui-pickers-x64.exe` | **选择器/上传/图片/媒体族演示**（18 控件，5 页） | **260,096 B（254 KB）** | **259,072 B** |
| `zzui-docs-x64.exe` | **三十八族演示**（18 页，单独产物以免顶穿 gallery 门槛） | **557,056 B（544 KB）** | **541,696 B** |

依据（实测）：控件层约 **1.1~1.7 KB/控件**，gallery 体积随控件数线性增长，
它衡量的是「把整个控件库都链进来要多少钱」，与「最小应用是否够小」是两个问题。
hello 的门槛**没有放宽**；gallery 的新门槛是在原口径失效后单列的，并在 `docs/决策记录.md` 留痕。
后续若继续加族，应优先考虑**按族拆多个示例产物**，而不是继续抬这个数字。

### 7.1 本次审计发现并已修的真问题

1. **线段预算先于节点预算被打满**：`table + charts` 同页时 `MAX_OVERLAYS`（192）被打满（实测 `lines=192/192`），
   版面看起来「图表缺一块」。根因是面积填充用粗线段（53 条/图）+ 圆弧 20 段/圈。
   **修法**：面积填充改**宽矩形条**（每 20px 一条，占节点预算 32 个/图，节点余量 152/256 更宽松）；
   圆弧收紧到 16 段/圈、半圆 12 段。修后实测 `nodes=152/256 cmds=266/512 lines=83/192 hits=16/128`。
2. **`MAX_OVERLAYS` 不能随便提**：从 192 提到 384 让 hello x64 **+13,824 B（+13.5 KB）**（实测），
   所以正确做法是**降绘制成本**，不是扩容。
3. **容量溢出必须可见**：给 `markOverflow` 加 Debug 打印后，同一测试 5 秒内就指出是 `overlays` 而不是 `nodes` ——
   没有这条打印只能靠猜。这条经验已写入项目记忆。

## 7. 建议的下一步（按「体积优先 + 高频优先」排序）

1. **平台**：X11/Cocoa 后端（需先在 WSL 里能实测 X11，否则按「实测优先」不开工）。

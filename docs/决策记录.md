## 2026-11-10 · 新约束：CUI（C 版）用 Zig 重写，产物体积尽可能小

**用户原话**：
> 「G:\Code\C\CUI  这个我我也想用Zig重写，但所有的都是需要打包后的尺寸都是要尽可能的小。」

**对象实测**（`G:\Code\C\CUI`，上游 `yappologistic/CUI`，MIT 许可，本地 `master` = `e8688b8`）：
- 规模：`src/*.c` **61 个文件 52,290 行**；`include/*.h` 4 个 **3,708 行**（`cui.h` 单文件 241 KB）；`third_party` 577 KB（`stb_image` / `stb_image_write` / `stb_rect_pack` / `stb_truetype`）。
- 形态：C99 **立即模式** UI 库，自述「约 190 个组件」；软件渲染器 + OpenGL 渲染器；后端 Win32 / Cocoa / X11 / SDL2 / GLFW。
- 上游体积纪律（`docs/architecture.md:158`）：每加代码都要量 `examples/hello` 在 `MinSizeRel` 下的增量；**核心不直接调用组件文件**（Windows 链接器按文件整体保留），可选功能由组件自己装 hook（如 `ui->emoji_hook`）。

**体积基线（本机实测，不是引用）**：
- 工具链：`zig cc`（Clang 22.1.8）+ CMake + Ninja，`-Os -DNDEBUG -Wl,--gc-sections -mwindows`，`MinSizeRel`，**无 LTO**（zig 链接器不接受 `-flto=auto`，已剔除后重建）。
- `examples/hello.exe` = **303,104 B（296.0 KB）**；加 `-s` 后字节数不变 → 无调试符号可剥。
- `libcui.a` = 2,167,792 B（2,117 KB）→ 体积靠链接期丢弃未用组件，库本身很大。
- 上游 README 自述「完整应用约 250 KB」，与实测 296 KB 同量级（差异来自缺 LTO 与编译器不同）。

**结论**：
1. **体积是第一约束**：以后每个 Zig 产物都要设体积上限，阈值写进回归脚本、只能收紧；每轮提交必须报实测字节数。
2. Zig 侧可行手段（**待逐个实测**，不预设结论）：`ReleaseSmall` + `strip`（ZZCOM 已验证）、GUI 子系统、不链 libc、按模块分文件避免整文件被保留、可选功能走 hook、数据表压缩（字体/emoji 走 `std.compress.flate`）。
3. **规模现实**：52,290 行 C、约 190 个组件，不可能一次搬完；必须分批，每批用 `zig build` + 体积对照卡住。

**待用户确认**（未落成结论）：
- ① CUI 是否作为 **ZZUI 的移植蓝本**（即 ZZUI 就是 CUI 的 Zig 版），还是另起独立仓库；
- ② 首批范围：骨架 + hello 等价物 / 核心组件子集（列出名单）/ 按目录逐个搬；
- ③ 平台范围：只做 Win32，还是保留多平台抽象。

## 2026-11-10 · 确认蓝本并要求多平台；里程碑 1 落地

**用户原话**：
> 「确认作为蓝本，现在开始」
> 「要做多平台的」

**决策**：
1. **CUI 是 ZZUI 的移植蓝本**；首批 = 骨架 + hello 等价物（与 `examples/hello.c` 同构）。
2. **必须多平台**：平台差异全部收敛到 `src/platform/*`，`core / render / widgets` 不引用任何平台 API；`platform.Backend` 用联合体分发，新增平台 = 加一个成员 + 一组同名方法。
3. **API 形态**：立即模式（CUI 原生形态的本味移植）——控件是函数、状态在调用方变量、输入对**上一帧矩形**判定。
4. **文本渲染取舍（体积优先）**：里程碑 1 由平台层用系统字体绘制（Win32 GDI），核心只发 `text` 指令；**不内嵌字体、不带 TTF 光栅器**。代价是跨平台视觉不完全一致；是否改为核心自带 TTF 光栅 + 内嵌字体列为待确认。

**里程碑 1 实际落地（文件清单）**：
- `build.zig`：x64 + x86 两个 exe，`optimize` 默认 `.small`（Zig 0.17 改为小写枚举）、`strip = true`、`subsystem = .windows`、`.abi = .gnu`（不链 libc）。
- `src/types.zig` / `theme.zig` / `core.zig`（节点、栈布局、绘制指令、命中判定、FNV-1a id）/ `render.zig`（BGRA 软件光栅、圆角）/ `widgets.zig`（heading / text / secondary / button / switch）/ `platform.zig` + `platform/win32.zig` + `platform/null.zig` / `bmpfile.zig`（Win32 落盘）。
- `src/win32.zig`：**复用 ZZCOM 已实测的 Win32 声明层**（681 行 → 追加 DIB/文本/鼠标消息），避免重写 100+ 个 extern。
- `examples/hello.zig`：窗口版 + `--once` 无窗口出图（写 `zzui-hello.bmp`）。

| `zig build test` | 3 个单测通过（column 栈叠、row 主轴、上一帧点击判定） |

**Zig 0.17 实际踩坑（写进记忆，避免下次重复）**：
- `std.lang.Optimize` 枚举值改为小写 `.debug/.safe/.fast/.small`（不再有 `.ReleaseSmall`）。
- 数组重复 `**` 已移除 → `@splat(...)`。
- `std.fs.cwd()` 在 0.17 不存在（新 IO 模型走 `std.Io.Dir` + `Io` 实例）→ 里程碑 1 的 BMP 落盘改用 `CreateFileW/WriteFile`（`src/bmpfile.zig`）。
- 对 `*union(enum)` 做 `switch (self)` 时 `|*b|` 捕获的是标签指针 → 要写 `switch (self.*)`。
- `SelectObject` 返回 `?HANDLE`，恢复旧对象要 `orelse`。

**与 CUI 的已知差异（里程碑 1 明确不做，后续对齐）**：
- 布局在构建时放置（CUI 是帧末统一布局 + 上一帧矩形回读）；
- 无状态回收、无弹簧动画、无深色主题、无键盘焦点/无障碍；
- 单窗口、无浮动层（popover/dialog）、无 OpenGL 渲染器；
- 只有 5 个控件，CUI 约 190 个。

**下一步（按体积门槛逐批推进）**：Cocoa / X11 后端 → 帧末布局与动画 → 基础控件族（checkbox/radio/slider/input）→ 容器与滚动 → 浮层（menu/dialog/tooltip）。

1. **`row` 里不能放 `column`（含 `card`）**：`open()` 取 `outer_w = parent.width`，嵌在 row 里会各占整行宽 → 卡片直接溢出窗口（首版 `metric` 就这样冲出了右边界）。卡片只在 column 里用，row 里要用绝对定位的 `panel`。

### 一、先修一个真 bug：覆盖层其实一直画在位图**下面**

上轮做裁剪框时我判断「位图在矩形之后画 → 改用 `addOverlayLine` 就好了」，**这个判断是错的**。

|---|---|---|

- 新增 `addOverlayBox(rect, opts)`：覆盖层现在也能画**填充矩形 + 边框**（`addOverlayLine` 只能画线），

## 2026-11-11（四）`cui_image.c` 全量：手写 BMP/TGA/PNG 解码（A/B 档 100% 收官）

**用户原话**：
> 「请继续」

### 一、口径先定：不用 stb_image

CUI 的 `cui_image_load` 走 stb_image（**291 KB 源码**，13 种格式）。用户对体积是硬要求，
所以本轮手写解码器 `src/image.zig`，并守住三条：

1. **不用 stb_image**：只实现真正需要的格式，代码由自己控；
2. **零堆分配**：像素缓冲 `out` 由调用方给，解码器只写不申请（与框架其余部分同一口径）；
3. **按需付费**：Zig 只编译**被调用到**的函数 —— 只调 `decodeBmp` 的产物不含 PNG 的 inflate。

### 二、实现范围（明确的边界，不假装更全）

| 格式 | 支持 | 明确不支持 |
|---|---|---|
| BMP | 24/32 bpp、BI_RGB、正/倒高度；32bpp 且首像素 alpha=0 时按不透明处理（老工具惯例） | RLE、位域、调色板、BITMAPCOREHEADER |
| TGA | 类型 2（未压缩）/ 10（RLE），24/32 bpp，可 top-down | 调色板、灰度 |
| PNG | 8 位通道、非隔行、color type 0/2/4/6 | 16 位、调色板、隔行、APNG |
| JPEG / GIF | **不支持**，返回 `error.Unsupported` | DCT/调色板动画的代价与体积都不合适 |

PNG 的两条现实约束（写进文档，不藏着）：
- `std.compress.flate` 的解压器**必须有 ≥ 64 KB 工作缓冲**（实测：传空缓冲会直接 panic 在
  `rebase` 的 `buffer.len - history_len` 下溢），所以 `scratch` = "IDAT 总长 + inflate 窗口"，
  由调用方给（`pngScratchSize(bytes)` 算得出来）；不藏在全局变量里，保持零分配与可重入；
- 多数编码器会把 IDAT 切成多个 8 KB 块，而 flate 流必须连续 → 解码器把各块拷进 `scratch` 前段。
- 单行上限 16,384 字节（4096 px RGBA），超了返回 `error.ImageTooWide`（栈上两行缓冲，不申请堆）。

### 三、体积实测（用户最关心的数字）

做法：把解码接进真实的 pickers 产物，做 A/B 对比（**不是**用合成的小程序——第一次那样做的探针
被 LLVM 把「只写全局、无人读」的解码调用整个 DCE 掉，量出来的是空程序的 4,608 B，
属于无效测量，记在这里避免重复踩）：

| 构建 | 体积 | 增量 |
|---|---|---|
| pickers（不解码） | 241,152 B | — |
| pickers + `decodeBmp` | **242,176 B** | **+1,024 B** |
| pickers + BMP + `decodePng` | 255,488 B | +13,312 B（PNG 那部分） |

结论：**BMP/TGA 几乎免费**（1 KB 级），PNG 的 inflate 值 13 KB —— 只有真要用 PNG 的产品才付。
所以示例里只演示 BMP 解码，PNG 走单测（9 项用例覆盖 RGB/RGBA/Sub 过滤/16 位拒绝/缓冲不足）。

`hello` / `gallery` 体积**完全不变**（177,664 / 318,464 B）：它们不引用解码器，Zig 不会把它链进去。

## 2026-11-11（六）动效核心 + **空闲节流**（顺手治理了主循环空转）

**用户原话**：
> 「请继续」

审计 §4 一直写着「动画：tween + spring（hover/press/focus 全插值）→ ZZUI **无**」；
用户级指令里也有「非必要不要经常性占用 CPU」。这两条其实是同一个问题的两面，本轮一起做。

### 一、`src/anim.zig`：按 id 的轨道池，指数趋近

- `Context.tracks[16]`（跨帧、**有界**、满了按「最久未使用」淘汰）+ `step/hover/toggle/mix/lerp`；
- **首次建立轨道时直接对齐目标** —— 否则一开窗所有控件都会从 0 淡入一遍（很难看，而且会让
  截图像素对不上）；只有**之后的变化**才走过渡；
- `dt` 夹到 0.1s（掉帧不瞬移），收敛后吸附到位（不留 0.9999 每帧重算）；
- **只插值颜色/透明度，不做几何位移**：本项目输入是「对上一帧矩形判定」，
  几何一动就容易出现「按钮跑掉了点不到」。

已接入：按钮（悬停底 + 按下）、开关（轨道色 + 滑块位置）、勾选框、单选框、页签（悬停底 + 选中下划线）、分段控件。

### 二、空闲节流：不烧 CPU 才是「资源惯例」

原来的主循环是 `PeekMessage` + `Sleep(1)` **无限空转**：即使界面完全静止，也每秒重建上千次
整个界面（720×1000 的软件光栅）。现在：

- `Context.need_frame`（每帧复位）+ `ui.requestFrame()`；
- `anim.step` 只要没收敛就自动 `requestFrame()`；
- 靠帧时间的控件全部补上：`spinner` / `toast`（ttl 计时）/ `tooltip`（延迟）/
  `hoverCard` / `confirmButton`（armed 超时）/ `levelMeter`（峰值保持）/
  `media.carousel`（吸附与自动轮播）/ `media.cardStack` / `media.counter` / `media.ticker`；
- `App.next`：`need_frame` 为假且没按住鼠标 → `backend.idle(50)`，
  Win32 用 **`MsgWaitForMultipleObjectsEx(0, null, 50, QS_ALLINPUT, 0)`**
  —— **有输入立即返回**，手感不变，CPU 从「一直满载」降到「按键才动」；
- 首帧 `need_frame = true`（`App.init` / `initHeadless`），启动不被节流挡 50ms。

**这条护栏必须留着**：`tests_anim.zig` 里有两项用例断言「过渡中 → need_frame 为真」、
「收敛后 / 行情条悬停暂停 → 为假」。忘了 `requestFrame` 的控件会「冻在动画中途」，
而这种 bug 在同步截图里看不出来 —— 只能靠断言守。

|---|---|---|---|
| hello x64 | 178,176 B | **180,224 B** | +2,048（动效 + 节流 API） |
| gallery x64 | 327,168 B | **329,216 B** | +2,048 |
| pickers x64 | 244,736 B | **246,784 B** | +2,048 |

门槛未动（gallery 329,216 < 335,872；pickers 246,784 < 253,952）。

### 四、踩坑

1. **动画一上来就会打乱截图断言**：`pickers:page4-accent` 从 33 掉到 **0** —— 页签下划线原本是
   `if (on) 画`，改成淡入后，截图只渲染 2 帧、`on_k ≈ 0`，于是什么都看不到。
   正解是「**首次观测直接对齐目标**」，而不是给截图加帧数。
2. **`win32.zig` 是手写声明层**（Zig 0.17 没有 `@cImport`），新 API 必须自己声明：

   会自动要求每个后端都实现 `idle`（新增后端漏了就编译失败）。
3. 又一次用「整行替换」的方式改 `win32.zig`，把两行粘在一起（`GetMessageW...;pub extern ... TranslateMessage`）。
   已当场用编辑工具修好 —— 这类机械替换要**带足够上下文**再动手。

## 2026-11-11（七）状态回收：跨帧状态池改 LRU，并挖出「焦点池被日历格子占满」

**用户原话**：
> 「请继续」

项目待办里剩「状态回收」。一查就发现三个**真实 bug**（都属「静默降级」，不报错、只是行为悄悄变错）：

| 池 | 原来的行为 | 后果 |
|---|---|---|
| `tips`（tooltip 计时） | 满了**直接不记**，返回当前时间 | 第 17 个 tooltip 永远不出现（每次都被当成「刚开始悬停」）|
| `scrolls`（滚动偏移） | 满了**返回槽 0** | 两个滚动区**共用同一个偏移**，一滚就串 |
| `focus_curr`（Tab 顺序） | 满了**静默丢弃**，无任何标记 | Tab 顺序悄悄少控件，查不出来 |

### 一、做法

- `TipState` / `ScrollState` 各加 `used: f64`；池满时**淘汰最久未使用**那条（与 `anim` 的轨道池同一策略），
  不再丢弃、也不再落回槽 0；
- `interactEx` 的焦点登记溢出改为 `markOverflow("focus")` —— 溢出变成**可观测**的（`ui.overflowed`）。

### 二、一改就炸出第二个真问题：日历格子占了整个焦点池

加上溢出标记后，`pickers:once` 直接返回 8（溢出）。顺着查：

- `month.zig` 与 `pickers.rangeCalendar` 的**每个日期格子**都是 `focusable = true`；
  两月日历 60+ 格 + 时分选择 36 格 + 两个滚轮 17 格 → 轻松破百；
- 于是 **Tab 键会在日历格子里逐格爬**，而后面真正的控件（输入框、按钮）全被挤出 Tab 顺序。

正解不是把池开得无限大，而是**别让列表项进 Tab 顺序**：
日期格、事件条、下拉项、滚轮行、命令面板项一律改成 `ui.interact(...)`（只响应鼠标），
Tab 停靠点保留在「整个日历 / 整个下拉框 / 整个滚轮」这一级。

### 三、代价（实测）

`MAX_FOCUS` 64 → **128**（dense 页面实测需要几十个，128 留一倍余量）：

| 产物 | 改前 | 改后 | 增量 |
|---|---|---|---|
| hello x64 | 180,224 B | **181,760 B** | +1,536 |
| gallery x64 | 329,216 B | **330,752 B** | +1,536 |
| pickers x64 | 246,784 B | **249,344 B** | +2,560（含 pickers 的 Tab 停靠点调整） |

（先试过 256：+3,584 B。容量常量会连带放大 `Context` 的初始化/搬运代码，
这与审计 §1.1 记的「`MAX_NODES` 变大 → 产物 +79 KB」是同一个现象，所以取 128 不取 256。）

### 四、护栏（新增 3 项）

`tests_state.zig`：
1. tooltip 池超过容量后，**最新那条仍被正确记住**（起始时间不变），最老的被淘汰；
2. 16 个滚动区各记各的偏移；再写第 17 个时**不串到别人的槽**（原来会写到槽 0），池仍有界；
3. 焦点池溢出时 `focus_curr_n == MAX_FOCUS` 且 `ui.overflowed == true`（不能静默）。

### 五、实测

- `zig build test`：**190 项**全绿；
- `zig build check`：四目标 exit 0；
- `REGRESSION PASSED (skip=0)`：gallery 13 页 + pickers 5 页 + 深色主题段全绿
  （说明把日历格移出 Tab 顺序没有破坏任何交互）。

## 2026-11-11（八）帧末回填尺寸 + C 档首两族（markdown / diff）

### 一、帧末回填尺寸（「帧末统一布局」在立即模式里的正确形态）

问题：`popoverBegin` 用调用方给的 `estimate_h` 猜高度去定位置、`dialog` 固定 176 高。
内容多一行就翻错方向或撑出卡片，而翻错方向**没有任何地方能发现**（不报错、不错位断言也测不到）。

为什么不能「帧末统一布局」照搬 CUI：CUI 有 retained 布局树，帧末才定位；立即模式必须
**先有 y 才能画**。所以取它的等价形态：**本帧画完量到真高 → 回填 → 下一帧用它定位**。

落地：
- `core.Context` 新增 `sizes: [8]SizeState` 池（`knownSize` / `rememberSize`，池满按 LRU 淘汰）。
  8 项是因为同时出现的绝对面板就一两个，而池越大 `Context` 越大（会连带抬高 `App` 拷贝代码）。
- `PanelOpts.size_key`：非 0 时 `close()` 里把**真实** `rect.w/h` 回填（`auto_height` 时用
  `cursor + pad*2`）。
- `overlay.popoverBegin`：`h = knownSize(key) orelse opts.estimate_h`，并把 `size_key` 交给 panel。
  于是**首帧**可能偏一点，**第二帧起就是真值**，不再有「估错就永远错」。
- `widgets.dialog`：`height: ?f32 = null`（默认按内容）。null 时首帧按「标题 + 消息换行行数 + 按钮行」
  估，第二帧起用真高居中，按钮紧跟内容；显式给值仍是老行为（固定高、按钮贴底）。

### 二、顺手补的字体能力：粗体 / 斜体

markdown 的 `**bold**` / `*italic*` 必须有字重差异，而 `addText` 只有 size + mono。

- 后端契约改动：`measure(s, size, bold)`（斜体按正体宽度量，误差可忽略；这样不必再改一次契约）。
- win32 `fontFor(size, mono, bold, italic)` → `CreateFontW` 第 6 参数（italic）+ 字重 600。

## 2026-11-11（九）C 档第三族：火焰图（cui_flame.c 的 flame graph 三件）

用户原话：**「请继续」**（接上一轮「其他的要全部迁移目标实现」）。

### 一、本轮范围

`cui_flame.c` 共 6 个公开 API，本轮做 **flame graph 三件**（重头、也最通用）：
`cui_flame_graph_ex` → `flame.flameGraph`、`cui_flame_sort` → `flame.sortSpans`、
`cui_flame_span_rect` → `flame.spanRect`。
未做：`cui_trace_view_ex` / `cui_trace_sort`（轨道式追踪视图）、`cui_waterfall_ex`（网络瀑布），下一轮。

### 二、与 CUI 的差异（有意为之）

| 项 | CUI | ZZUI |
|---|---|---|
| 缩放/适配动画 | tween（`cui__fl_animate_to` + `cui__fl_lerp`）| **不做动画**，直接跳到目标范围 |
| 键盘 | ←/→ 行内移动、↑↓ 走父子、Shift+箭头平移、Esc 清选、Enter 缩放到选中 | 只保留 **←/→ 切选中、←/→ 自动 reveal、+/- 缩放、Home/F 适配** |
| 细条合并 | 比一个像素还窄的合并成中性条 | 直接按像素映射（细条被裁掉）|
| 垂直滚动 | 拖拽上下平移 | 保留 `View.scroll` 字段但本版不做滚轮映射（滚轮留给缩放）|
| 悬浮提示 | CUI tooltip | 自绘小卡片（不走 `widgets.tooltip` 的 0.35s 延迟）|

### 三、实现要点

- **命中不做逐条**：整块面板一个 `interact`，条的位置由鼠标坐标反算（`hitTest`）——
  这和 `MAX_HITS`(128) 的教训一致：网格/条带类控件**不能每条一个命中**。
- **条色由名字哈希决定**：`hsl(hue = key % 360, s = 0.40, l = 0.40/0.74)`，
  同一个函数名永远同色，深浅色主题各一档亮度。不引入 series 色板（多一组令牌多一份体积）。
- **刻度不使用对数**：`niceStep` 用「反复除 10」求 1/2/5×10^n，避免 `@log10` 拖进数学库。
- **拖拽/双击用尺寸池记状态**：`rememberSize(pid ^ 0xF1A3, mouse_x, view.start - t0)` 与
  `rememberSize(pid ^ 0xF1A4, now_ms, mouse_x)` —— 不为两个交互在 `Context` 里加字段。

### 四、实测

| 项 | 值 |
|---|---|
| 单测 | **214 项**（新增 7 项 flame） |
| docs x64 | 208,384 → **220,672 B**（+12,288，火焰图族） |

### 一、正则（`src/regex.zig`，对位 `cui_regex_search`）

自写回溯引擎，**零堆分配**：模式编译进固定节点池（128 个节点），匹配用「区间 + 位置」递归。
支持字面量/转义、`.`、`[]`/`[^]` 含区间、`\d \w \s \D \W \S`、`\b \B`、`^ $`、
`( )` / `(?: )` / `(?<name> )`、`|`、量词 `* + ? {n} {n,} {n,m}`（都能加 `?` 变惰性）。
步数上限 20 万，超了返回 `too_slow` 而不是卡死。

**踩了两个结构性坑（都靠测试抓出来的，记下来免得下次重犯）**：
1. **repeat 必须包住「原子自己」而不是「原子在序列里的位置」**：第一版把量词节点追加在原子之后，
   序列匹配时原子先被吃一次、repeat 又重复 N 次 → `a{2,3}` 在 "aaaa" 匹配出 4 个字符。
   改成「先给 repeat 占位，再解析原子并把原子区间交给它」，序列里只留 repeat 一个节点。
2. **零宽断言（`^ $ \b`）不能被「空匹配保护」判死**：原逻辑 `if (np == pos) break;` 会让
   `count` 停在 0 → `count < min` → 恒失败（`^b`、`\bcat\b` 全都不匹配）。
   改成「零宽算一次成功，但不继续循环」。

与 CUI 的差异：**按字节匹配**（`. `、`\w` 是 ASCII 语义）；**没有正则测试器控件**
（`cui_regex_tester_ex` 是「模式框 + 高亮文本 + 匹配列表」的组合界面，与编辑器族一起做更合适）。

### 二、顺手改掉的三处真实问题

1. **`regex.Match.group_start/group_end` 的注释是错的**：写「1 基」，实际写入是
   `caps[k*2]`，而 `caps` 里 `gidx==0`（整体命中）**不占槽**，第 1 个分组就在 `[0]`。
   我按注释写成了 `group_start[g]`，测试立刻抓到（`group_start[1]` 拿到的是第 2 组）。
   已把注释改成 0 基，并在 `regextester` 里统一 `g-1`。
2. **`lang = "text"` 名不副实**：`langOf` 已返回 `.plain`，但 `tokenize` 仍会给数字/引号上色 ——
   正则测试器的样本是**任意文本**，着色纯属干扰。现在 `tokenize(.plain)` 直接整行一个 run。
3. **`editor` 改文本后摘要慢一帧**：`run()` 排在编辑器之前（这样标记与它对应的文本始终一致），
   但编辑器在本帧改了文本时，摘要/列表会拿旧结果。改为 `if (ed.changed) run(...)` 再补算一次 ——
   摘要与列表**同帧正确**，高亮仍滞后一帧（避免指到新文本的错位色块，这是有意的取舍）。

### 二、顺手做的两处「同一逻辑去重」

1. **`dateFromDays` 原来只有 `pickers.zig` 一份**（Howard Hinnant 的 civil_from_days）。
   周历/甘特都要「天数 → 日期」，于是下沉成 **`month.fromDays`**（与 `month.daysFromCivil` 成对），
   `pickers.dateFromDays` 改为转调，`planning` 直接用 —— 不再出现第二份实现。
2. **语义色映射复用 `trace.toneColor`**（改为 `pub`）：日历事件与甘特任务条用同一套 8 色，
   不会出现「同一语义两种色」。形状上不复制 CUI 的 `cui__tone_color`。

### 三、四个实战坑（都靠截图/测试抓出来）

1. **行内格式化文本必须 `ui.frameStr`**（这条已经踩过两次）：小时刻度与日号用同一个栈缓冲，
   不拷进帧池的话**所有行都显示最后一个值**（第一版截图里七列日期全是 `15`、每个刻度都是 `14:0`）。
2. **文本层按字符串画，不会被节点宽裁切**：事件标题超宽会压到隔壁格子（第一版 "Design review"
   直接盖住 "Port review"）。新增 `fitText(ui, s, size, max_w)`：按测量宽逐字符回退 + `...`，
   并在 UTF-8 续字节上不切。
3. **`ncol` 要带自己的 `colk+1` 起算**：只按「与别人的重叠」取 max，会把正在第二栏的事件算成 1 栏，
   于是两个同时开始的事件被画成 95px + 95px 而不是 45px + 45px（测试断言宽度直接抓到）。
4. **`@memcpy(cb[0..c1.len], c1)` 自我别名**：`num.int` 已经写进 `cb` 并返回它的子切片，
   再拷一次会 panic（`@memcpy arguments alias`）。

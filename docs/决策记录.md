## 2026-11-10 · 接入远端仓库并推送

**用户原话**：
> 「https://github.com/RemoteAll/ZZUI.git 这个是仓库地址」

**落地（实测）**：
- `git remote add origin https://github.com/RemoteAll/ZZUI.git`；`git push -u origin main` → `* [new branch] main -> main`，push exit 0。
- 接入前探测：`git ls-remote --heads/--tags` 均**为空**（远端是空仓库）→ 无需合并历史，直接推送本地 3 个提交。
- 跟踪关系 `/ 一致性`：`git rev-parse --abbrev-ref @{u}` = `origin/main`；本地 `HEAD` 与远端 `refs/heads/main` 均为 `04ae4fc…`。
- remote 命名用 `origin`（与同级 `ZZCOM` 一致）；核对远端一律用 `git rev-parse --abbrev-ref --symbolic-full-name '@{u}'`，不硬编码 `origin/<分支>`。
- 文档同步：`docs/项目接续指南.md`「远程仓库」、`.github/copilot-instructions.md`「项目现状」写入地址；`docs/用户档案.md` 待确认项去掉远端地址。

## 2026-11-10 · 评估：ZZCOM 的 UI 代码能否迁移（结论待确认，未动手）

**用户原话**：

**不可迁移（串口工具业务）**：
- `main.zig` L218-566：`createControls` 225 行 + `layout` 124 行，全是 ZZCOM 界的固定 96dpi 绝对坐标 → 只能当「布局写法示例」，**不是布局引擎**；
- `main.zig` L606-1633（1028 行）：状态/串口/发送/历史/批量/定时/配置/文件/循环/MCP/高级设置/命令；
- `serial.zig` 369 行、`mcp.zig` 335 行、`mcp_http.zig` 142 行、`config/log/text` 322 行。

**结论**：**可以迁**，约 600 行已验证的 Win32/DPI/控件代码（含 Win7+ 与不链 libc 的坑点沉淀）值得搬。但现在这套是「应用直接对 `?HWND` 写流程」：
- 无控件抽象（裸句柄 + 自由函数）、无事件抽象（`onCommand` 大 switch）、无布局引擎（手写坐标）、无主题层（`WHITE_BRUSH` + 黑字写死）；
- 这四层正是「框架」的本体，**必须新写**，迁移只能省掉底层封装的重复劳动。

**边界约定（重要）**：搬过来后 `ZZCOM` 最终应**反向依赖 ZZUI**（复用优先、同逻辑不许两份），但必须等 ZZUI 抽象稳定后再切；**本轮只搬、不改 ZZCOM**，避免把 ZZCOM 拖进设计变更。

**建议路线（每步可回归）**：
1. 低风险搬运：`src/win32/{types,const,ui,gdi}.zig` + 空窗口样例，`zig build` 通过；
2. 抽基础层：`ui/{widget,dpi,dialog}.zig`（`Widget` 包装 HWND + 类型 + 布局参数），API 保持薄；
3. 框架本体：布局/主题/事件分发 + 300 行样例（标签/按钮/编辑框/状态栏），再让 ZZCOM 反向接入验证。

**待用户确认**：① 是否按此 3 步开工；② API 风格（保留模式控件树 vs 立即模式）；③ 是否只做 Win32（不跨平台）。
